# Decision log

| # | Decision | Reason in business terms | Rejected alternative |
| --- | --- | --- | --- |
| 1 | Infrastructure deployed by CloudFormation Git sync | Every change is a reviewed pull request; the repository is the record of what runs | Console changes (untracked); a CLI run from a laptop (no review, no history) |
| 2 | App CI pushes the image and deploy bundle; an ECR push of `:latest` starts CodePipeline through EventBridge | A developer merges and the change is tested, scanned and released, with every release recorded in one place | Editing an image tag in the infra repository for every release (slow, easy to forget); building again inside AWS (two build systems) |
| 3 | Each release's task definition is rendered from the live revision (deploy bundle: `taskdef.json` + `appspec.yaml`) | Roles, sizes and secrets stay owned by the infra repository; the app repository only swaps the image | Task definition JSON in the app repository (duplicates ARNs and sizes owned by infra) |
| 4 | ECR tags mutable: each image is tagged with its git SHA, and `latest` moves to the release | Every running task can be traced to the exact code; a release for the same commit can be re-run (CodeDeploy deploys by image digest) | Immutable tags (re-running a release for the same commit fails when the SHA tag is pushed again) |
| 5 | Tests and a CRITICAL-vulnerability scan (Trivy) gate every image | Broken or known-vulnerable code never reaches customers | Scan after deploy only |
| 6 | CodeDeploy blue/green with test listener, automatic rollback on alarms, old version kept 5 minutes | Customers never see a half-deployed version; a bad release rolls back by itself or with one click | Rolling update (old and new mixed; rollback is a new deployment) |
| 7 | Platform split into five nested stacks, one per domain (network, database, edge, storage, application) | Each domain can be read, reviewed and changed on its own; every resource lives with the ones it belongs to | One 1,000-line template (hard to review); separate top-level stacks with exports (exports block changes between stacks) |
| 8 | Nested templates published to S3 by CI under a content hash, write-once | What Git says and what CloudFormation runs are always the same files | Uploading by hand; overwriting one fixed S3 path (a running change could pick up the wrong file) |
| 9 | `scripts/bootstrap.sh` builds everything in a fixed order with placeholder stacks | Rebuild from the repository with two commands; Git sync only updates stacks that already exist | A README of manual CLI steps |
| 10 | GitHub Actions uses OIDC; Git sync uses CodeConnections | No AWS access keys stored anywhere | IAM users with access keys |
| 11 | AWS WAF on the ALB checks CloudFront's secret origin header | CodeDeploy swaps only the listener's default action, so the header check cannot be a listener rule; WAF keeps the ALB closed to everything except Onward's CloudFront (about USD 6 a month) | Security group only (any CloudFront distribution could reach the ALB); CloudFront VPC origin (bigger change) |
| 12 | App `.env` values in SSM Parameter Store (`/onward/<env>/app/*`), injected by ECS; credentials stay in Secrets Manager | One place to see and change configuration per environment; a change needs no new task definition, which a CodeDeploy-controlled service cannot take from CloudFormation | Plain environment variables in the task definition (every change is a task definition change); a `.env` file in the image (configuration baked into the build) |
